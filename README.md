# CV Screener

A single Next.js app that lets a recruiter ask natural-language questions about a corpus of
28 generated CV PDFs and get grounded, source-cited answers back through a streaming chat UI.

Built as an end-to-end RAG prototype: generate the CVs → extract & chunk their text → embed
locally → retrieve by cosine similarity → answer through an LLM constrained to the retrieved
excerpts.

## What it is

- **28 fake candidate CVs** (`data/cvs/*.pdf`), generated by an LLM and rendered to PDF —
  varied roles, seniority, nationalities, and languages, with a few edge cases seeded on
  purpose (e.g. several Python users, four candidates who attended UPC) so the demo questions
  below have real answers to find.
- **A retrieval index** (`data/index.json`, 168 chunks) built by extracting text from those
  PDFs, splitting on section headings, and embedding each chunk with a local MiniLM model —
  no external embedding API, no vector database.
- **A chat API** (`app/api/chat/route.ts`) that embeds the recruiter's question, retrieves the
  top-scoring chunks, and asks an OpenRouter chat model to answer *only* from those excerpts —
  it's told to say so plainly when the CVs don't contain the answer, rather than invent facts.
- **A chat UI** (`app/page.tsx`) with streaming markdown answers and source chips per answer
  (candidate + section) that link to the underlying PDF.

## Quickstart

```bash
npm install
cp .env.example .env      # then add your OPENROUTER_API_KEY (see below)
npm run dev
```

Open [http://localhost:3000](http://localhost:3000).

Notes:

- `data/cvs/*.pdf` and `data/index.json` are already committed, so **you do not need to
  regenerate the corpus** to run the chat feature — `npm install && npm run dev` is enough to
  get the UI and retrieval working end to end.
- You **do** need an `OPENROUTER_API_KEY` even with the pre-built corpus: `lib/openrouter.ts`
  throws at import time if the env var is unset, and the chat route imports it, so any question
  sent to `/api/chat` will fail without a key. The UI itself loads fine either way.
- Only regenerating the CV corpus needs `npx playwright install chromium` (see below) — it's
  not required for a normal `npm run dev`.
- This repo's env file convention is `.env` (Next.js loads both `.env` and `.env.local`
  automatically, with `.env.local` taking precedence). `.env.example` is the template; either
  filename works, `.env` is what's used here.
- `npm run dev` runs `next dev --webpack` rather than the Turbopack default — a deliberate
  workaround for the local embeddings model loader (`@huggingface/transformers`), not a
  regression to "fix".

## Regenerating the dataset

Only needed if you want a fresh set of candidates/CVs, or want to see the generation pipeline
run yourself.

```bash
npx playwright install chromium   # one-time, for PDF rendering
npm run generate-cvs              # LLM profiles -> HTML -> data/cvs/*.pdf (~28 candidates)
npm run ingest                    # data/cvs/*.pdf -> data/index.json (chunks + vectors)
```

Costs: `generate-cvs` makes OpenRouter calls for both text (candidate JSON, batched 7 at a
time) and images (one headshot per candidate, with a styled-initials-avatar fallback if an
image call fails). Using the free-tier model defaults in `lib/openrouter.ts`, this is free but
rate-limited — expect retries and a few minutes end to end. `ingest` is local-only (PDF text
extraction + MiniLM embedding) and costs nothing.

## Architecture

```mermaid
flowchart TD
    subgraph gen["Generation (offline, one-time)"]
        LLM[OpenRouter chat model] -->|candidate JSON, zod-validated| GC[scripts/generate-cvs.ts]
        IMG[OpenRouter image model] -->|headshot or avatar fallback| GC
        GC -->|HTML template + Playwright print-to-PDF| PDFS[(data/cvs/*.pdf<br/>28 CVs)]
    end

    subgraph ing["Ingestion (offline, one-time)"]
        PDFS -->|extractText, unpdf| ING[scripts/ingest.ts]
        ING -->|split on section headings| CHUNKS[section chunks<br/>candidate + section metadata]
        CHUNKS -->|local MiniLM<br/>lib/embeddings.ts| VEC[384-dim vectors]
        VEC --> IDX[(data/index.json<br/>168 chunks)]
    end

    subgraph chat["Chat request (runtime)"]
        UI[app/page.tsx<br/>useChat + DefaultChatTransport] -->|POST /api/chat| ROUTE[app/api/chat/route.ts]
        ROUTE -->|embed query, local MiniLM| EMB[lib/embeddings.ts]
        EMB -->|query vector| RANK[lib/retrieval.ts<br/>cosine top-k]
        IDX -.loaded once, cached in memory.-> RANK
        RANK -->|top-scoring, above-threshold chunks| PROMPT[grounded system prompt]
        PROMPT -->|excerpts only, cite by name, refuse if absent| LLM2[OpenRouter chat model<br/>lib/openrouter.ts]
        LLM2 -->|streamed answer + source metadata| UI
        UI -->|source chips, candidate + section| PDFROUTE[app/api/cvs/[file]/route.ts]
        PDFROUTE -->|serves original PDF| PDFS
    end
```

Local MiniLM (`Xenova/all-MiniLM-L6-v2` via `@huggingface/transformers`) does both the
ingestion-time chunk embeddings and the runtime query embedding — no OpenAI/embedding API
calls, no network round trip. OpenRouter (via the AI SDK) is used only for the chat completion
(and, offline, for CV generation).

## Design decisions

- **Local embeddings, not an embedding API.** MiniLM runs in-process via transformers.js.
  Benchmarked on this machine: query embedding ~1–3 ms, cosine search <2 ms over ~300 vectors,
  full index build <1 s. Zero marginal cost, works offline, and keeps the `Embedder` interface
  (`lib/embeddings.ts`) swappable if a hosted model is ever needed.
- **No vector database.** ~300 vectors × 384 dimensions fits comfortably in memory as a JSON
  file (`data/index.json`, loaded and cached once per process by `lib/retrieval.ts`). A real
  vector DB (LanceDB, pgvector, etc.) is the obvious next step at a larger corpus size, not at
  this one.
- **No RAG framework.** The retrieval-to-prompt pipeline is ~40 lines of hand-rolled
  TypeScript (`app/api/chat/route.ts`): embed → cosine top-k → filter by score → build a
  grounded system prompt → stream a completion. No LangChain/LlamaIndex — at this scale a
  framework would add indirection without solving a problem the direct code doesn't already
  solve simply.
- **Grounding rule.** The system prompt instructs the model to answer only from the retrieved
  excerpts and to say plainly when the CVs don't mention something, rather than guess. A
  `MIN_SCORE` threshold (0.25) on retrieval also gates this at the source: if nothing scores
  above threshold, the model is handed no excerpts and has nothing to hallucinate from. `TOP_K`
  is kept generous (15) relative to `MIN_SCORE` so it never silently truncates chunks that
  already cleared the relevance bar — `MIN_SCORE`, not `TOP_K`, is the actual relevance gate.

## Project structure

```
leadtech/
├── app/
│   ├── page.tsx                  # Chat UI: message list, input, suggestion chips
│   ├── components/source-chips.tsx
│   └── api/
│       ├── chat/route.ts         # RAG endpoint: retrieve -> grounded prompt -> stream
│       └── cvs/[file]/route.ts   # Serves a CV PDF by filename (for source chip links)
├── lib/
│   ├── embeddings.ts             # Embedder interface + local MiniLM implementation
│   ├── retrieval.ts              # IndexedChunk/RetrievedChunk types, cosine top-k
│   ├── openrouter.ts             # OpenRouter client + model id config
│   └── chat-types.ts             # ChatMessage / SourceRef shared types
├── scripts/
│   ├── generate-cvs.ts           # OpenRouter -> candidate JSON -> HTML -> PDF
│   ├── cv-schema.ts              # zod schema + generation prompt
│   ├── cv-template.ts            # HTML template variants
│   ├── chunker.ts                # PDF text -> section-aware chunks
│   └── ingest.ts                 # Orchestrates extraction -> chunking -> embedding -> index
├── data/
│   ├── cvs/*.pdf                 # 28 generated CVs (committed)
│   └── index.json                # 168-chunk vector index (committed)
└── docs/
    └── video-outline.md          # 5-minute walkthrough script
```
